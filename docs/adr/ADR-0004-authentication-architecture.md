# ADR-0004: Два контура аутентификации — Users и Admin

| Поле | Значение |
|---|---|
| Статус | Accepted |
| Дата | 2026-07-21 |
| Идентификатор по ТЗ | HM-ADR-001 (Authentication Architecture) |
| Авторы | HouseMaster Team |
| Связано | 000-system-overview.md (v1.2), 002-gcp-architecture.md, ADR-0002, ADR-0003 |
| Заменяет | Модель «единая Workspace-аутентификация» из 000 v1.0–v1.1 |

## Контекст

С первой версии архитектуры (HM-ARCH-001) действовало допущение: *все* пользователи HouseMaster входят через Google Workspace домена `abay-germes.kz`, и «пользователь существует в системе, только если существует в Workspace-домене».

При проработке HM-005 допущение оказалось ошибочным. Анализ модели эксплуатации выявил два принципиально разных класса пользователей:

1. **Пользователи платформы** — клиенты HouseMaster: председатель ОСИ, хаузмастер, инженер, бухгалтер ОСИ, техник. Они **не являются сотрудниками Abay Germes**, не имеют и не должны иметь аккаунтов в корпоративном Workspace. Их почта — любая: Gmail, Outlook, Yandex, корпоративная.
2. **Внутренние пользователи** — сотрудники Abay Germes: разработчики, DevOps, поддержка, администраторы, операторы, бухгалтерия. Именно они живут в Workspace `abay-germes.kz`.

Старая модель содержала внутреннее противоречие уже в v1.0: роль *OSI Chairman* числилась среди пользователей системы при требовании Workspace-членства для входа — председатель ОСИ не может быть заведён в корпоративный домен управляющей компании.

### Какие проблемы создавала единая Workspace-аутентификация

- **Экономическая:** каждый клиент платформы требовал бы платного аккаунта в Workspace Abay Germes — стоимость растёт линейно с числом клиентов и оплачивается не клиентом.
- **Организационная:** заведение/увольнение председателей ОСИ и техников чужих организаций в корпоративном каталоге компании — административный абсурд и нарушение границ ответственности.
- **Безопасность:** членство в корпоративном домене давало бы клиентам потенциальный доступ к внутренним ресурсам Google Workspace компании (диски, группы, календари).
- **Масштабирование:** модель «один домен = все пользователи» несовместима с целевой мультиарендностью (много ОСИ, в перспективе — много управляющих компаний).

## Решение

Аутентификация разделяется на **два независимых контура** с разными требованиями доверия:

```text
                          HouseMaster
                       PWA / Web Client
                              │
                              ▼
                       HouseMaster API
                              │
            ┌─────────────────┴──────────────────┐
            │                                    │
            ▼                                    ▼
   ┌─────────────────────┐            ┌─────────────────────────┐
   │  HouseMaster Users  │            │    HouseMaster Admin    │
   │  (контур клиентов)  │            │  (контур сотрудников)   │
   ├─────────────────────┤            ├─────────────────────────┤
   │ любой e-mail        │            │ ТОЛЬКО Google Workspace │
   │ Google OAuth        │            │ abay-germes.kz          │
   │ Email + Password    │            │ Internal OAuth client   │
   │ верификация e-mail  │            │ server-side hd check    │
   │ JWT-сессия          │            │ JWT-сессия              │
   │ RBAC (роли клиентов)│            │ Admin RBAC              │
   └─────────────────────┘            └─────────────────────────┘
```

1. **Контур Users** — для клиентов платформы. Способы входа: Google OAuth (любой Google-аккаунт, `hd` не проверяется) и Email + Password (регистрация, подтверждение e-mail, восстановление пароля). Требует хранения пользователей → зависит от Cloud SQL (ADR-0003).
2. **Контур Admin** — для сотрудников Abay Germes. Только Google Workspace: OAuth-клиент типа *Internal* в GCP-проекте организации (первый эшелон — Google сам не пускает чужих) + серверная проверка claim `hd` из ID-токена (второй эшелон). Логика проверки — `isAllowedDomain(hd)` с заменяемым источником списка доменов (сегодня — конфигурация, при мультиарендности — БД); алгоритм при расширении не меняется.
3. Оба контура выдают JWT-сессии единого формата с обязательным признаком контура (`realm: user | admin`); авторизация (RBAC) — на стороне приложения, набор ролей у контуров непересекающийся.
4. **Google Workspace остаётся только административным контуром.** Обоснование: для сотрудников это даёт корпоративный жизненный цикл доступа (увольнение из домена = потеря доступа), 2FA-политики организации и нулевую стоимость поддержки паролей — ровно те свойства, которые нужны контуру с повышенными привилегиями и бессмысленно навязывать клиентам.

### Почему новая схема масштабируется лучше

Рост числа клиентов не создаёт ни расходов на Workspace-лицензии, ни записей в корпоративном каталоге. Появление второй управляющей компании (мультиарендность) — это данные в таблице организаций, а не новый домен в конфигурации. Контуры эволюционируют независимо: клиентам можно добавить вход через телефон/eGov без единого изменения в админ-контуре.

## Последствия

- **Roadmap:** прежняя задача HM-005 «Google Workspace Login» разделена: **HM-005 — Admin Portal Authentication** (Workspace, без БД — выполнима сейчас) и **HM-006 — HouseMaster User Authentication** (Email + Google OAuth + Registration + Password Reset). HM-006 **зависит от Cloud SQL** (хранение пользователей и хэшей паролей) и от механизма отправки почты (верификация, сброс пароля) — выполняется после HM-GCP-003.
- **Периметр админ-контура** должен быть отделён на уровне маршрутов (`/admin/*`) с собственным middleware; сессия контура Users не даёт доступа к админ-маршрутам ни при какой роли.
- Контур Users обязан включать защиты, ненужные в Workspace-модели: хэширование паролей (argon2id), rate limiting на вход и регистрацию, верификацию e-mail до активации, защиту от перебора при сбросе пароля. Детали — в спецификации HM-006.
- Документы 000 (v1.2) и 002 приведены в соответствие; формулировка «пользователь существует только в Workspace» изъята из всех документов (см. аудит в отчёте задачи).
- Инфраструктура (Terraform, Secret Manager и пр.) **не меняется**: секреты `google-client-id/secret` обслуживают админ-контур; секреты контура Users (второй OAuth-клиент, SMTP) добавятся в HM-006 отдельным изменением.

## Отклонённые альтернативы

| Вариант | Почему отклонён |
|---|---|
| Заводить клиентов в Workspace Abay Germes | Стоимость, административный абсурд, риск доступа к внутренним ресурсам — см. «Проблемы» |
| Identity Platform / Firebase Auth для контура Users | Возврат экосистемы, исключённой ADR-0002; Auth.js покрывает оба контура одним стеком без нового вендора внутри приложения |
| Один контур «любой Google-аккаунт» для всех, роли решают всё | Теряется первый эшелон защиты админ-периметра (Internal client + hd); привилегированный доступ нельзя вешать на одну лишь прикладную проверку роли |
