# ADR-0003: Cloud SQL (PostgreSQL) как основная операционная БД

| Поле | Значение |
|---|---|
| Статус | Accepted |
| Дата | 2026-07-21 |
| Авторы | HouseMaster Team |
| Связано | ADR-0002, 000-system-overview.md (обновлён до v1.1), 001-domain-model.md (план) |
| Заменяет | Выбор Firestore, зафиксированный в 000-system-overview.md v1.0 |

## Контекст

В первой версии системного обзора (HM-ARCH-001, v1.0) операционной БД был назначен Firestore. При проработке GCP-архитектуры (HM-GCP-001) выбор БД был пересмотрен, поскольку доменная модель HouseMaster оказалась выраженно **реляционной**:

```
Дом → Подъезды → Этажи/Помещения
Дом → Инженерные системы → Оборудование
Осмотр → Дефекты → Работы → Материалы
Дефект → Норматив (СНиП/ГОСТ) → Метод ремонта
```

Ключевые запросы системы — соединения и агрегации по этим связям: «все открытые дефекты системы отопления по домам серии 464», «история работ по стояку», «дефекты без назначенных работ старше 30 дней». Кроме того, акты и отчёты требуют транзакционной целостности (акт + дефекты + подписи — одна атомарная операция).

## Решение

1. Основная операционная БД — **Cloud SQL for PostgreSQL**.
2. **BigQuery** остаётся аналитическим хранилищем (статистика, отчётность по фонду) и наполняется из PostgreSQL (federated queries / batch export).
3. **Firestore из архитектуры исключается.** Документ 000-system-overview.md обновлён (v1.1).
4. Доступ из приложения — через Cloud SQL connector; учётные данные — в Secret Manager; локальная разработка — обычный PostgreSQL в Docker.

## Обоснование

| Критерий | Cloud SQL (PostgreSQL) | Firestore |
|---|---|---|
| Реляционная доменная модель, JOIN'ы | Нативно | Денормализация, дублирование данных |
| Транзакции между сущностями | Полные ACID | Ограниченные, в пределах модели документов |
| Сложные выборки и агрегации | SQL | Требует предрасчёта/дублирования |
| Геоданные (дома на карте, перспектива) | PostGIS | Только geo-точки, без гео-запросов |
| Расширения под AI | pgvector как запасной вариант к Vector Search | Нет |
| Переносимость (митигация lock-in по ADR-0002) | Стандартный PostgreSQL | Проприетарный API |
| Офлайн-синхронизация PWA | Реализуется на уровне приложения (очередь) | Встроенная — единственное значимое преимущество |
| Стоимость на старте | Минимальный инстанс — постоянная плата | Pay-per-use, дешевле при нулевой нагрузке |

Единственные ощутимые преимущества Firestore — встроенный офлайн-sync и нулевая стоимость простоя — не перевешивают: офлайн-очередь PWA всё равно проектируется на уровне приложения (осмотры «в поле» — это черновики, синхронизируемые пакетно), а стоимость минимального инстанса Cloud SQL приемлема и предсказуема.

## Последствия

- В стек добавляется ORM/миграции (Prisma или Drizzle — выбор будет зафиксирован отдельным ADR при старте бизнес-логики) и дисциплина схемы БД.
- `001-domain-model.md` проектируется сразу как реляционная схема (ER-модель).
- Cloud SQL размещается в приватной сети (private IP), доступ из Cloud Run — через connector; публичного доступа к БД нет.
- Появляется постоянная статья расходов (минимальный инстанс в dev может останавливаться вне рабочих часов через Cloud Scheduler).
- Встроенный офлайн-sync Firestore не используется; офлайн-режим PWA реализуется через локальное хранилище браузера и API пакетной синхронизации.
