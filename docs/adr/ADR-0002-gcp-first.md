# ADR-0002: GCP First — ориентация платформы на Google Cloud

| Поле | Значение |
|---|---|
| Статус | Accepted |
| Дата | 2026-07-21 |
| Авторы | HouseMaster Team |
| Связано | 000-system-overview.md, 002-gcp-architecture.md, ADR-0003 |
| Уточнено | ADR-0004: Google Workspace — только административный контур; клиенты платформы входят с любым e-mail |

## Контекст

HouseMaster — AI-first платформа сопровождения эксплуатации жилого фонда. Ядро продукта — мультимодальный AI-конвейер (анализ фото, OCR документов, RAG по нормативам) и корпоративная идентичность через Google Workspace. Необходимо выбрать облачную платформу до завершения MVP, чтобы архитектура приложения (аутентификация, хранение, AI-интеграции, конфигурация) с первого дня строилась под целевую среду и не требовала переделки.

Рассматривались варианты: GCP, AWS, Azure, self-hosted/гибрид.

## Решение

**HouseMaster строится исключительно на Google Cloud Platform.** Все инфраструктурные и AI-зависимости выбираются из экосистемы Google:

- вычисления — Cloud Run;
- данные — Cloud SQL (PostgreSQL, см. ADR-0003), BigQuery, Cloud Storage;
- AI — Vertex AI (Gemini, Vision, Document AI, Embeddings, Vector Search);
- идентичность — **Google Workspace OAuth** для административного контура (*уточнение ADR-0004*; Identity Platform не используется);
- секреты — Secret Manager; наблюдаемость — Cloud Logging / Monitoring;
- CI/CD — Cloud Build + Artifact Registry; асинхронность — Pub/Sub + Cloud Scheduler.

Firebase **не используется** — ни для аутентификации, ни для данных, ни для хостинга.

## Обоснование

1. **AI-стек.** Vertex AI закрывает весь конвейер HouseMaster (мультимодальные модели Gemini, Document AI для OCR нормативов, Vector Search для RAG) как управляемые сервисы одного вендора — без склейки API трёх разных провайдеров.
2. **Идентичность.** Организация уже живёт в Google Workspace. Workspace OAuth даёт сотрудникам корпоративный вход «из коробки»: увольнение из домена автоматически закрывает доступ. (*С ADR-0004 это относится к административному контуру; клиенты платформы аутентифицируются независимо от Workspace.*)
3. **Единый контур безопасности.** IAM, service accounts, Secret Manager, Audit Logs — одна модель разграничения доступа от CI/CD до вызова модели.
4. **Zero-ops.** Cloud Run и управляемые БД снимают эксплуатацию серверов с команды из нескольких человек.
5. **Меньше интеграционных швов.** Каждый стык «вендор A ↔ вендор B» — это отдельные SDK, биллинг, аутентификация и точка отказа. Моновендорность на этапе становления платформы дешевле в разработке и сопровождении.

## Рассмотренные альтернативы

| Вариант | Почему отклонён |
|---|---|
| AWS | Сильная платформа, но AI-стек (Bedrock) и идентичность потребовали бы интеграции с Google Workspace через федерацию; больше швов при отсутствии преимуществ для нашего кейса |
| Azure | Аналогично: экосистема ориентирована на Microsoft 365, а не Google Workspace |
| Self-hosted / гибрид | Неприемлемая операционная нагрузка для размера команды; потеря управляемого AI-стека |
| Firebase (внутри Google) | Дублирует выбранные сервисы (Auth vs Workspace OAuth, Firestore vs Cloud SQL), тянет собственную экосистему SDK; отклонён явно |

## Последствия

- **Vendor lock-in принят осознанно.** Митигируется стандартными интерфейсами: PostgreSQL (переносимая СУБД), контейнеры (OCI), S3-совместимый доступ к Storage, инфраструктура как код (Terraform).
- Все новые зависимости проверяются на вопрос «есть ли управляемый аналог в GCP» до подключения сторонних сервисов.
- Локальная разработка использует эмуляцию/локальные аналоги (локальный PostgreSQL, заглушки AI) — приложение не должно требовать GCP для запуска dev-среды.
- Инфраструктура описывается в Terraform в отдельном репозитории; в монорепо хранится только конфигурация CI (`cloudbuild.yaml`, `infrastructure/cloudbuild/`).
