## Terminology

Единый словарь документа. Термины используются строго в соответствии с этими определениями.

| Термин | Определение |
|---|---|
| **Service Context** | Архитектурный контекст служебных данных об объектах и организациях. Физически размещён в GCP. |
| **Personal Context** | Архитектурный контекст персональных данных физических лиц. Физически размещён на серверах в РК. |
| **Context Boundary** | Физическая и логическая граница между Service Context и Personal Context. ПДн не пересекают эту границу. |
| **Reference Identity** | UUID-идентификатор, используемый как ссылка между контекстами без передачи персональных данных. |
| **Cross-context Communication** | Любое взаимодействие между Service Context и Personal Context. Допускается только через Reference Identity и агрегированные данные. |
| **Service Data** | Данные об организациях, объектах инфраструктуры, осмотрах, работах. Хранятся в Service Context. |
| **Personal Data (ПДн)** | Данные, прямо или косвенно идентифицирующие физическое лицо. Хранятся исключительно в Personal Context. |
| **KZ Contour** | Физическое размещение Personal Context на серверах в Казахстане. Термин используется только в контексте развёртывания. |

## Architectural Principles

Принципы, определяющие данное решение и все производные от него.

**1. Separation of Contexts.**
Персональные данные физических лиц и служебные данные об объектах принадлежат разным доменам. Они хранятся в физически разделённых контекстах. Смешение контекстов недопустимо.

**2. GCP First, Personal Context Where Required.**
GCP — основная платформа для Service Data, AI-конвейера и вычислений. Personal Context размещается на серверах в Казахстане в соответствии с Законом РК №94-V. Это точная граница GCP-стратегии, а не отступление от неё.

**3. Context Boundary is Physical, Not Policy.**
ПДн не попадают в Service Context через архитектуру, а не через правила и фильтры. Граница контекстов — физическая граница хранения.

**4. Personal Context is Provider-Neutral.**
Personal Context использует только возможности PostgreSQL, не препятствующие миграции между провайдерами. Прикладная логика не зависит от конкретного провайдера KZ Contour.

**5. No Personal Data in AI Pipeline.**
AI-сервисы получают только Service Data и обезличенные агрегаты. Передача ПДн в AI-конвейер запрещена без исключений.

**6. Context Autonomy.**
Каждый контекст функционирует при недоступности другого. Деградация допустима; повреждение данных — нет.

**7. Application is the Only Crossing Point.**
Единственная точка взаимодействия между контекстами — прикладной код. Прямые сетевые соединения между хранилищами разных контекстов запрещены.

## Context

HouseMaster — цифровая операционная платформа для управления жилым фондом Республики Казахстан с горизонтом 5–10 лет. Система обслуживает два класса пользователей с принципиально разными требованиями: сотрудников организаций (Admin Portal) и физических лиц — жителей домов (PWA).

Платформа ориентирована на интеграцию с государственными сервисами РК, операторами связи и коммунальными платформами — что создаёт долгосрочные требования к суверенитету данных.

Ключевые факты на дату принятия ADR:
- GCP выбран как основная платформа (ADR-0002), Cloud SQL как операционная СУБД (ADR-0003)
- Двухконтурная аутентификация реализована: Admin через Google Workspace, Users — независимый контур (ADR-0004)
- GCP не имеет региона на территории Казахстана
- GCP-инфраструктура развёрнута и содержит рабочие данные

---

## Problem Statement

Принятая GCP-архитектура создаёт коллизию с Законом РК №94-V: персональные данные граждан РК должны храниться на серверах на территории РК. Cloud SQL в регионе `europe-west3` (Германия) этому требованию не соответствует.

Без архитектурного решения реализация HM-006 приведёт к записи ПДн жителей в GCP — что создаёт юридический риск и блокирует интеграции с государственными сервисами РК.

Существует и доменный аргумент, независимый от законодательства: физические лица (жители) и юридические лица (организации, объекты) принадлежат разным доменам с разными требованиями жизненного цикла, доверия и обработки. Смешение их в единой схеме данных — структурная проблема.

## Decision

Система разделяется на два физически независимых архитектурных контекста по доменному критерию — **субъект данных**.

```
┌─────────────────────────────────────────────────────────────┐
│                     SERVICE CONTEXT                         │
│              Service Data · Субъект: организация            │
│                                                             │
│   Organization · House · Entrance                           │
│   Asset · Inspection · WorkOrder                            │
│   Reference Identities (UUID)                               │
│                                                             │
│   AI Layer: Vertex AI · Vector Search · Knowledge Base      │
│   Platform: Cloud Run · Pub/Sub · Storage · Monitoring      │
│                                                             │
│   Физическое размещение: GCP (europe-west3)                 │
└─────────────────────────────┬───────────────────────────────┘
                              │
                   Cross-context Communication
                   Reference Identity only · No PII
                              │
┌─────────────────────────────┴───────────────────────────────┐
│                    PERSONAL CONTEXT                         │
│            Personal Data · Субъект: физическое лицо         │
│                                                             │
│   Данные физических лиц                                     │
│   Аутентификация и идентификация жителей                    │
│   История обращений                                         │
│   Данные сессий                                             │
│                                                             │
│   Физическое размещение: KZ Contour                         │
│   (серверы на территории РК, провайдер определяется         │
│    отдельным решением)                                       │
└─────────────────────────────────────────────────────────────┘
```

### Ключевые решения

**Критерий классификации — субъект данных.** Service Data (данные о юрлицах и объектах) → Service Context. Personal Data (данные о физлицах) → Personal Context. Критерий применяется к каждой новой сущности при проектировании.

**Cross-context Communication только через Reference Identity.** Между контекстами передаются исключительно UUID-идентификаторы. Реляционных FK между контекстами нет. Согласованность данных обеспечивается на уровне прикладной логики.

**Приложение — единственная точка пересечения.** Прямые соединения между хранилищами разных контекстов запрещены. Только прикладной код, работающий с двумя независимыми клиентами данных.

**Personal Context технологически нейтрален.** Используются только возможности PostgreSQL, не препятствующие миграции между провайдерами. Прикладная логика не содержит зависимостей от конкретного KZ-провайдера.

**AI-конвейер изолирован от Personal Data.** Vertex AI и смежные сервисы получают только Service Data и обезличенные агрегаты.

## Decision Scope

Данный ADR определяет исключительно архитектурные границы системы — принцип разделения контекстов и правила их взаимодействия.

ADR сознательно не определяет:

- структуру Prisma Schema и конкретные модели данных
- механизм синхронизации между контекстами
- механизм и протокол защищённого канала
- выбор KZ-провайдера
- реализацию авторизации и RBAC
- детали Terraform и IaC KZ-контура
- CI/CD и deployment topology
- паттерн `StaffRef` или иной способ хранения ссылок в Service Context

Эти вопросы решаются отдельными ADR и инженерными задачами, принимающими данный документ как базовое ограничение.

## Architectural Invariants

Инварианты — обязательные правила, нарушение которых требует выпуска нового ADR. Они не могут быть переопределены инженерными решениями уровня задач.

**Invariant 1 — Personal Data Isolation.**
Personal Data физических лиц никогда не попадает в Service Context. Это правило не имеет исключений и не может быть смягчено конфигурацией или политикой.

**Invariant 2 — AI Data Purity.**
AI-сервисы получают только Service Data и обезличенные агрегаты. Personal Data в AI-конвейер не передаётся ни напрямую, ни косвенно.

**Invariant 3 — Reference-Only Cross-context Communication.**
Взаимодействие между контекстами осуществляется исключительно через Reference Identity (UUID) и агрегированные данные. Передача Personal Data через Context Boundary запрещена.

**Invariant 4 — Provider Independence of Personal Context.**
Прикладная логика не зависит от конкретного провайдера Personal Context. Смена провайдера — конфигурационное изменение, не требующее модификации кода.

**Invariant 5 — Context Autonomy.**
Отказ одного контекста не приводит к повреждению данных другого. Деградация функциональности допустима; атомарность данных каждого контекста сохраняется независимо.

**Invariant 6 — Application as Sole Crossing Point.**
Единственная точка взаимодействия между контекстами — прикладной код. Прямые соединения между хранилищами разных контекстов на уровне БД запрещены.

**Invariant 7 — Invariant Enforcement.**
Нарушение любого из инвариантов 1–6 требует выпуска нового ADR с явным обоснованием и анализом последствий. Обход инварианта в рамках инженерной задачи недопустим.

## Rejected Alternatives

### A. Единый Service Context (все данные в GCP)

**Идея:** сохранить всё в Cloud SQL, упростить операционную модель.

**Достоинства:** единый ORM, единые миграции, полная FK-целостность, лучшая производительность.

**Причина отказа:** прямое нарушение Закона РК №94-V — Personal Data хранилась бы на серверах в Германии. Риск неустраним без смены архитектуры. Блокирует интеграции с государственными сервисами РК.

### B. Единый Personal Context (всё в Казахстане)

**Идея:** перенести всё хранение в KZ, GCP использовать только для вычислений и AI.

**Достоинства:** полное соответствие Закону №94-V, отсутствие cross-context сложности.

**Причина отказа:** AI-конвейер требует доступа к Service Data — возникает обратный поток из KZ в GCP, не устраняющий cross-context сложность, а перемещающий её. Теряются преимущества управляемого Cloud SQL. Доступность KZ-инфраструктуры исторически ниже GCP.

### C. Анонимизация Personal Data в GCP

**Идея:** хранить данные в GCP, обезличивая ПДн перед записью.

**Достоинства:** единый контекст, операционная простота.

**Причина отказа:** анонимизированные данные теряют функциональность личного кабинета. Псевдонимизация ≠ анонимизация — её достаточность для соответствия Закону №94-V требует отдельного правового заключения. Юридический риск не устраняется.

### D. Ожидать GCP-региона в Казахстане

**Идея:** отложить решение до появления GCP-региона на территории РК.

**Причина отказа:** нет публичного roadmap и гарантий сроков. Блокирует HM-006 на неопределённый срок. Выбранная архитектура обеспечивает более простую миграцию при появлении региона, чем переход от единого GCP к разделённой схеме с реальными данными.

## Trade-offs

| Приобретаем | Принимаем |
|---|---|
| Соответствие Закону РК №94-V | Два независимых pipeline развёртывания |
| AI-конвейер без юридических ограничений | Cross-context запросы = два round trips |
| Независимость от KZ-провайдера | Согласованность на уровне приложения, не СУБД |
| Готовность к интеграциям с госсервисами РК | Два набора схем и миграций |
| Автономность контекстов при сбоях | Операционный налог на команду |
| Переносимость прикладной логики | Отсутствие FK между контекстами |

## Architectural Evolution

Архитектура спроектирована для развития без пересмотра базовых принципов. Следующие изменения совместимы с данным ADR:

**Третий контекст.** При появлении новых требований (например, federated государственный реестр, партнёрский контекст) применяется тот же критерий — субъект данных. Принципы Cross-context Communication и Context Boundary распространяются на любое количество контекстов.

**GCP Kazakhstan Region.** Personal Context переносится в Cloud SQL в KZ-регионе без изменения прикладной логики — только конфигурация. Физическое разделение контекстов сохраняется: это архитектурное требование, а не следствие отсутствия GCP в РК.

**Смена KZ-провайдера.** Принцип provider-neutrality Personal Context обеспечивает смену провайдера без изменения кода. Провайдер — сменяемый инфраструктурный компонент.

**Несколько регионов хранения ПДн.** При международном развёртывании Personal Context может быть распределён по юрисдикциям. Принципы ADR применяются к каждой юрисдикции независимо.

**Новые AI-компоненты.** Любые новые AI-сервисы подчиняются Invariant 2: работают только с Service Data и обезличенными агрегатами.

**Интеграции с госсервисами и операторами связи.** Интеграции, требующие локализации данных, подключаются к Personal Context. Технические и аналитические данные — к Service Context через обезличенные агрегаты.

Во всех сценариях Architectural Invariants 1–6 остаются неизменными.

## Accepted Defaults

Три вопроса, ранее блокировавшие принятие ADR, закрыты осознанными решениями по умолчанию. Детальная проработка каждого — отдельные задачи, не блокирующие архитектурное решение.

### 1. Применение Закона РК №94-V к данным ОСИ

**Принятое решение по умолчанию:** архитектурное разделение контекстов внедряется превентивно на основании буквального прочтения ст. 22 Закона №94-V. Персональные данные физических лиц — граждан РК — размещаются на серверах в Казахстане. Это решение верно при любой интерпретации Закона и создаёт более сильную позицию чем ожидание юридического заключения.

**Следующий шаг:** юридическая консультация по специфике ОСИ — отдельная задача, результат которой может только расширить допустимое (но не сузить принятое решение).

### 2. Выбор провайдера Personal Context (KZ Contour)

**Принятое решение по умолчанию:** провайдер не фиксируется на уровне ADR. ADR требует только физического размещения в РК и соответствия принципу provider-neutrality (Invariant 4). Конкретный провайдер выбирается при развёртывании Personal Context в рамках HM-006 и оформляется операционным решением, не новым ADR.

**Кандидаты на момент принятия:** iD Host, Kazakhtelecom, QazCloud. Критерии выбора: SLA, стоимость, PostgreSQL 15+, физическое расположение в РК.

### 3. Механизм защищённого канала между контекстами

**Принятое решение по умолчанию:** канал реализуется на уровне приложения (HTTPS/TLS между Cloud Run и Personal Context API). ADR фиксирует только принцип — взаимодействие только через Reference Identity, только через прикладной код (Invariant 6). Конкретный сетевой механизм (прямой TLS, VPN, mTLS) определяется при выборе провайдера и не влияет на архитектурное решение.

### 4. Политика резервного копирования Personal Context

**Принятое решение по умолчанию:** резервное копирование Personal Context выполняется на серверах в РК. Периодичность, retention и инструменты — операционное решение при развёртывании.

## Context Diagram Notes

*Рекомендации по обновлению `context-architecture.svg` при следующей редакции диаграммы. Архитектурное решение не меняется.*

**`StaffRef` → `Reference Identity (UUID)`.** Конкретная модель данных (`StaffRef`) не должна фигурировать на контекстной диаграмме — это уровень реализации. Заменить на нейтральный термин `Reference Identity` или `Cross-context ID`.

**Google Workspace — External Integration.** Google Workspace является внешней интеграцией Admin Portal, а не частью архитектурного контекста системы. На контекстной диаграмме пометить как `External` или перенести в отдельную Integration View.

**`UUID only` на стрелке → `Cross-context Communication`.** Метка на стрелке должна отражать архитектурный принцип, а не технический механизм. `Cross-context Communication` более точно и не фиксирует реализацию.

**Уровень абстракции GCP-компонентов.** `Pub/Sub`, `Secret Manager` — это инфраструктурный уровень. На контекстной диаграмме достаточно `Platform Services`. Детализация — в Infrastructure Diagram.
