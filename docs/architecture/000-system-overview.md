## Mission

**HouseMaster — интеллектуальная система сопровождения эксплуатации жилых домов Республики Казахстан.**

HouseMaster — это не CRM, не HelpDesk и не корпоративный сайт. Это **AI Assistant** — цифровой инженер, который сопровождает весь жизненный цикл эксплуатации многоквартирного жилого дома: от первичного осмотра и фиксации дефектов до формирования актов, подбора нормативной базы и рекомендаций по ремонту.

Ключевая задача системы — превратить разрозненные знания об эксплуатации жилого фонда (фотографии, документы, проекты, нормативы СНиП/ГОСТ, опыт инженеров) в единую машиночитаемую базу знаний и предоставить к ней доступ через естественный язык и мультимодальные интерфейсы.

Система создаётся для реалий жилищно-коммунального хозяйства Казахстана: типовые серии домов, институт ОСИ (объединения собственников имущества), национальная нормативная база, казахский и русский языки.

## Vision

HouseMaster станет **цифровым инженером ЖКХ** — полноценным AI-участником процесса эксплуатации зданий.

В горизонте нескольких лет система сможет:

- **понимать фотографии** — распознавать конструкции, инженерные узлы и дефекты на снимках с объектов;
- **понимать документы** — читать акты, паспорта зданий, проектную и исполнительную документацию;
- **понимать проекты домов** — работать с типовыми сериями и проектными решениями конкретных зданий;
- **понимать инженерные сети** — отопление, водоснабжение, канализацию, электроснабжение, вентиляцию, лифтовое хозяйство;
- **искать дефекты** — сопоставлять наблюдения с базой типовых дефектов и историей объекта;
- **предлагать решения** — рекомендовать методы ремонта, материалы и оборудование;
- **формировать отчёты** — автоматически собирать отчёты по осмотрам и состоянию зданий;
- **создавать акты** — генерировать акты осмотра и дефектные ведомости по шаблонам;
- **искать нормативы** — находить релевантные положения СНиП, ГОСТ и национальных стандартов;
- **общаться естественным языком** — вести диалог с инженером, мастером и председателем ОСИ.

Долгосрочная цель — переход от реактивной модели («сломалось — чиним») к **предиктивной эксплуатации** и, в перспективе, к цифровым двойникам зданий.

## Core Principles

| Принцип | Что означает для HouseMaster |
|---|---|
| **Cloud Native** | Система изначально проектируется под облако: контейнеры, serverless, управляемые сервисы, инфраструктура как код (Terraform). Никаких «серверов в подвале». |
| **AI First** | AI — не надстройка, а ядро продукта. Каждый рабочий процесс проектируется с вопросом: «Что здесь может сделать модель?» |
| **Google Ecosystem** | Единый вендор инфраструктуры и AI: Google Cloud Platform, Vertex AI; Google Workspace — идентичность административного контура ([ADR-0004](../adr/ADR-0004-authentication-architecture.md)). Минимум интеграционных швов. Решение зафиксировано в [ADR-0002](../adr/ADR-0002-gcp-first.md). |
| **Knowledge Driven** | Ценность системы определяется качеством базы знаний. Данные — актив первого класса; наполнение и курирование базы знаний — отдельный процесс. |
| **Scalable** | От одного дома до жилого фонда города и страны без смены архитектуры. Горизонтальное масштабирование на уровне Cloud Run и Vector Search. |
| **Secure** | Два контура аутентификации с разными требованиями доверия (клиенты / сотрудники), OAuth2, RBAC, IAM, аудит. Безопасность закладывается на уровне архитектуры, а не «прикручивается» потом. |
| **Offline First (PWA)** | Мастер работает в подвалах и на техэтажах без связи. Приложение — PWA с локальным кэшем и отложенной синхронизацией. |
| **API First** | Все возможности системы доступны через API. UI — лишь один из клиентов. Это открывает путь мобильным клиентам, интеграциям и будущим агентам. |

JWT-сессии с признаком контура. | Auth.js, OAuth2, RBAC, GCP IAM |
| **Storage** | Хранение медиа и документов: фото дефектов, видео осмотров, сканы актов, проектная документация. | Cloud Storage (бакеты по типам контента, lifecycle-политики) |
| **Monitoring** | Наблюдаемость системы: логи, метрики, трассировки, алерты, аудит действий пользователей. | Cloud Logging, Cloud Monitoring, Error Reporting, Audit Logs |

## User Roles

| Роль | Описание | Ключевые возможности |
|---|---|---|
| **Administrator** | Администратор системы | Управление пользователями и ролями, настройка организации, доступ ко всем данным, аудит |
| **Engineer** | Инженер по эксплуатации | Планирование и анализ осмотров, работа с дефектами, нормативами, актами, полный доступ к AI-инструментам |
| **HouseMaster** | Мастер / хаузмастер на объекте | Осмотры «в поле»: фото, фиксация дефектов, чек-листы, офлайн-режим, быстрые консультации с AI |
| **OSI Chairman** | Председатель ОСИ | Просмотр состояния дома, отчёты, согласование работ, история осмотров |
| **Inspector** | Инспектор / проверяющий | Доступ на чтение к актам, отчётам и нормативному соответствию объектов |
| **Resident (future)** | Житель (перспектива) | Подача заявок, просмотр статуса работ по своему дому, уведомления |

Роли делятся по контурам аутентификации ([ADR-0004](../adr/ADR-0004-authentication-architecture.md)): **Engineer, HouseMaster, OSI Chairman, Inspector, Resident** — контур *Users* (клиенты платформы, любой e-mail; сюда же — бухгалтер ОСИ и техник как варианты ролей); **Administrator** и внутренние роли (DevOps, поддержка, операторы) — контур *Admin* (только сотрудники Abay Germes через Google Workspace). RBAC реализуется в базе приложения; наборы ролей контуров не пересекаются, сессия контура Users не даёт доступа к админ-маршрутам ни при какой роли.

## Authentication

Аутентификация разделена на **два независимых контура** с разными требованиями доверия — решение и обоснование в [ADR-0004](../adr/ADR-0004-authentication-architecture.md):

```text
                          HouseMaster
                       PWA / Web Client
                              │
                              ▼
                       HouseMaster API
                              │
            ┌─────────────────┴──────────────────┐
            ▼                                    ▼
   ┌─────────────────────┐            ┌─────────────────────────┐
   │  HouseMaster Users  │            │    HouseMaster Admin    │
   │      (клиенты)      │            │ (сотрудники Abay Germes)│
   ├─────────────────────┤            ├─────────────────────────┤
   │ любой e-mail        │            │ ТОЛЬКО Google Workspace │
   │ Google OAuth        │            │ Internal OAuth client   │
   │ Email + Password    │            │ server-side hd check    │
   │ JWT (realm: user)   │            │ JWT (realm: admin)      │
   │ RBAC клиентских     │            │ Admin RBAC              │
   │ ролей               │            │                         │
   └─────────────────────┘            └─────────────────────────┘
```

**Контур Users — клиенты платформы** (председатель ОСИ, хаузмастер, инженер, бухгалтер ОСИ, техник):

- вход через **Google OAuth** (любой Google-аккаунт, домен не проверяется) или **Email + Password**;
- регистрация с обязательной верификацией e-mail; восстановление пароля;
- пароли — argon2id, rate limiting на вход/регистрацию/сброс;
- Google Workspace **не требуется** — клиент не обязан иметь никакого отношения к корпоративным системам Abay Germes;
- хранение пользователей — Cloud SQL ([ADR-0003](../adr/ADR-0003-cloud-sql-postgresql.md)); контур реализуется задачей **HM-006** после появления БД.

**Контур Admin — сотрудники Abay Germes** (разработчики, DevOps, поддержка, администраторы, операторы):

- вход **только** через Google Workspace домена организации;
- два эшелона защиты: OAuth-клиент типа *Internal* (Google сам отклоняет аккаунты вне организации) + серверная проверка claim `hd` из ID-токена в callback `signIn` (`hd` в параметрах запроса — лишь UX-фильтр);
- проверка домена — функция `isAllowedDomain(hd)` с заменяемым источником данных: сегодня конфигурация, при мультиарендности — БД; алгоритм не меняется;
- жизненный цикл доступа корпоративный: увольнение из Workspace-домена автоматически закрывает доступ;
- админ-маршруты (`/admin/*`) — отдельный периметр со своим middleware; реализуется задачей **HM-005**.

**Общее для обоих контуров:** JWT-сессии единого формата с обязательным признаком контура (`realm`); RBAC в базе приложения (Google и пароль отвечают «кто ты», приложение — «что тебе можно»); сервисные учётные записи GCP — по модели least privilege (IAM); все значимые действия журналируются.

Детальная модель безопасности — в `005-security.md`.

## Data Flow

Базовый поток обработки запроса пользователя:

```text
User
  │  действие в интерфейсе (вопрос, фото, форма осмотра)
  ▼
Authentication
  │  контур Users: Google OAuth или Email+Password;
  │  контур Admin: Google Workspace + серверная
  │  проверка hd (ADR-0004)
  ▼
JWT
  │  выпуск сессионного токена с идентичностью и ролью,
  │  токен сопровождает каждый последующий запрос
  ▼
API
  │  валидация токена, проверка прав (RBAC),
  │  валидация входных данных, маршрутизация запроса
  ▼
Business Logic
  │  доменные операции: осмотр, дефект, акт, отчёт;
  │  решение, нужен ли AI и какие знания привлечь
  ▼
Knowledge Base
  │  выборка контекста: данные объекта, история дефектов,
  │  релевантные документы и нормативы (в т.ч. через Vector Search)
  ▼
Vertex AI
  │  вызов модели с собранным контекстом (RAG):
  │  анализ, генерация ответа, рекомендации, черновик документа
  ▼
Response
  │  постобработка: структурирование, ссылки на источники,
  │  сохранение результата в базе (история, аудит)
  ▼
UI
     отображение пользователю; при офлайн-сценарии —
     запись в локальную очередь PWA и синхронизация позже
```

Принципиальные свойства потока:

1. **Ни один запрос не минует аутентификацию и RBAC** — проверка прав происходит в API-слое до бизнес-логики.
2. **AI никогда не отвечает «из воздуха»** — модель получает контекст из базы знаний (RAG), а ответы сопровождаются ссылками на источники.
3. **Все значимые действия журналируются** — кто, когда, с каким объектом и с каким результатом.

## AI Pipeline

AI-конвейер — ядро системы. Он состоит из двух основных потоков: визуального и документного. Оба сходятся в общем векторном индексе, что и делает RAG **мультимодальным**: текстовый вопрос может находить фотографии дефектов, а фотография — текстовые нормативы.

### Визуальный конвейер (фото и видео с объектов)

```text
Photo
  │  снимок дефекта/узла с осмотра (метаданные: дом,
  │  подъезд, система, автор, время, геопозиция)
  ▼
Vision AI
  │  мультимодальный анализ: что изображено, признаки
  │  дефекта, состояние конструкции/оборудования
  ▼
Embeddings
  │  векторное представление изображения и его описания
  │  (мультимодальные эмбеддинги Vertex AI)
  ▼
Vector Search
  │  поиск похожих случаев: типовые дефекты, история
  │  этого дома и этой серии, прецеденты ремонта
  ▼
LLM
  │  Gemini собирает картину: классификация дефекта,
  │  вероятные причины, применимые нормативы
  ▼
Recommendation
     рекомендация: срочность, метод ремонта, материалы,
     ссылки на нормативы и похожие случаи
```

### Документный конвейер (нормативы, паспорта, акты, проекты)

```text
Document
  │  СНиП, ГОСТ, паспорт здания, проектная документация,
  │  акт осмотра (PDF, скан, фото документа)
  ▼
OCR
  │  извлечение текста и структуры (Document AI);
  │  распознавание таблиц, разделов, реквизитов
  ▼
Chunking
  │  разбиение на смысловые фрагменты с сохранением
  │  контекста (документ, раздел, пункт норматива)
  ▼
Embeddings
  │  векторизация фрагментов (text embeddings Vertex AI)
  ▼
Vector Search
  │  индексация; при запросе — семантический поиск
  │  релевантных фрагментов по смыслу, а не по словам
  ▼
Gemini
  │  генерация ответа строго на основе найденных
  │  фрагментов (grounded RAG), с цитированием пунктов
  ▼
Answer
     ответ с ссылками на конкретные документы и пункты
     нормативов; черновики актов и отчётов
```

Ключевые архитектурные решения AI-слоя (подробно — в `003-ai-architecture.md`):

- **RAG вместо fine-tuning** как базовая стратегия: знания живут в базе, а не в весах модели — их можно обновлять, проверять и цитировать.
- **Единый векторный индекс** для текста и изображений — основа кросс-модального поиска.
- **Обязательное цитирование источников** — каждая рекомендация инженерного характера прослеживается до норматива или прецедента.
- **Человек принимает решение** — AI формирует рекомендации и черновики; акты и решения о работах утверждает человек соответствующей роли.

## Knowledge Base

База знаний — главный актив HouseMaster. Она объединяет разнородные типы знаний в единое семантическое пространство:

| Категория | Содержание | Форма хранения |
|---|---|---|
| **Photos** | Фотографии дефектов, узлов, конструкций с привязкой к объекту и системе | Cloud Storage + метаданные в PostgreSQL + эмбеддинги в Vector Search |
| **Videos** | Видео осмотров, обходов, работы оборудования | Cloud Storage + метаданные |
| **Building Series** | Типовые серии домов РК: конструктивные особенности, типовые узлы, известные слабые места | Структурированные записи + документы серий |
| **SNIP** | СНиП и СН РК — строительные нормы и правила | OCR → чанки → векторный индекс |
| **GOST** | ГОСТы и национальные стандарты | OCR → чанки → векторный индекс |
| **Building Passports** | Технические паспорта конкретных зданий | Структурированные данные + сканы |
| **Engineering Documentation** | Проектная и исполнительная документация, схемы инженерных сетей | Cloud Storage + индекс |
| **Typical Defects** | Каталог типовых дефектов: признаки, причины, развитие, критичность | Структурированный справочник + связанные фото |
| **Repair Methods** | Методы устранения дефектов: технологии, последовательность, требования | Структурированный справочник |
| **Equipment** | Оборудование зданий: котлы, насосы, лифты, узлы учёта — модели, регламенты обслуживания | Справочник + документация производителей |
| **Manufacturers** | Производители и поставщики оборудования и материалов | Справочник |
| **Materials** | Строительные и ремонтные материалы: характеристики, применимость, нормы расхода | Справочник |
| **Inspection Acts** | Акты осмотров: как исторические данные и как обучающие прецеденты | Структурированные записи + сканы |
| **Instructions** | Инструкции по эксплуатации, регламенты, чек-листы осмотров | Документы + структурированные чек-листы |

Принципы базы знаний:

1. **Каждый факт имеет источник** — документ, акт, наблюдение или норматив.
2. **Знания связаны** — дефект ссылается на серию дома, метод ремонта, материалы и норматив; фото — на дефект и объект.
3. **База растёт от использования** — каждый осмотр, фото и акт пополняют её; система становится умнее с каждым обследованным домом.
4. **Курирование обязательно** — нормативные и справочные данные проходят проверку инженером до включения в «доверенный» контур RAG.

Устройство базы знаний и стратегия её наполнения — предмет `004-knowledge-base.md`.

## Deployment

Конвейер поставки полностью автоматизирован и построен на сервисах GitHub + GCP:

```text
GitHub
  │  монорепо приложения (Turborepo: apps/*, packages/*)
  │  + отдельный репозиторий Terraform (инфраструктура)
  │  push / merge в main
  ▼
Cloud Build
  │  CI: установка зависимостей, линт, тесты,
  │  сборка Docker-образа приложения
  ▼
Artifact Registry
  │  версионированное хранение контейнерных образов
  ▼
Cloud Run
  │  serverless-развёртывание: автоскейлинг от нуля,
  │  ревизии, канареечные релизы, откат одной командой
  ▼
Cloud Storage
  │  статические ассеты, медиа, документы
  ▼
Vertex AI
     управляемые модели и векторный индекс —
     не деплоятся с приложением, версионируются отдельно
```

Свойства модели развёртывания:

- **Инфраструктура как код** — вся конфигурация GCP описана в Terraform и проходит тот же review-процесс, что и код приложения.
- **Неизменяемые артефакты** — каждый релиз это конкретный образ в Artifact Registry; откат = переключение ревизии Cloud Run.
- **Среды** — как минимум `dev` и `prod` как отдельные GCP-проекты с идентичной Terraform-конфигурацией.
- **Zero-ops** — отсутствуют серверы, требующие обслуживания; масштабирование и обновление платформы — ответственность Google.

Скелеты `Dockerfile` и `cloudbuild.yaml` подготовлены в корне репозитория (HM-GCP-001); реализация — на фазе развёртывания.

## Technology Stack

| Слой | Технология | Роль в системе |
|---|---|---|
| Frontend | **Next.js** | PWA, SSR/SSG, маршрутизация, API routes |
| Язык | **TypeScript** | Единый типобезопасный язык фронтенда и бэкенда |
| UI | **Tailwind** | Дизайн-система и стилизация |
| Аутентификация | **Auth.js** | OAuth2-интеграция с Google-провайдером, сессии |
| Идентичность | **Google Workspace** | Поставщик идентичности административного контура ([ADR-0004](../adr/ADR-0004-authentication-architecture.md)); клиенты — любой e-mail |
| Вычисления | **Cloud Run** | Serverless-контейнеры для приложения и сервисов |
| Файлы | **Cloud Storage** | Медиа, документы, статика |
| AI-платформа | **Vertex AI** | Gemini (LLM), Vision, Document AI, эмбеддинги |
| Семантический поиск | **Vector Search** | Векторный индекс базы знаний, основа RAG |
| Аналитика | **BigQuery** | Аналитическое хранилище: статистика дефектов, отчётность |
| Операционная БД | **Cloud SQL (PostgreSQL)** | Реляционная БД: объекты, осмотры, дефекты, пользователи, роли ([ADR-0003](../adr/ADR-0003-cloud-sql-postgresql.md)) |
| Репозитории / CI | **GitHub** | Код, ревью, триггеры CI/CD |
| Контейнеризация | **Docker** | Упаковка приложения для Cloud Run |

Дополнительно в проекте используются **Turborepo + pnpm** (организация монорепозитория) и **Terraform** (инфраструктура как код) — как инструменты разработки и эксплуатации, не входящие в рантайм системы.

## Future Roadmap

```text
Phase 1 — Authentication (два контура, ADR-0004)
  │  HM-005: Admin Portal Authentication — Google Workspace,
  │          Internal client, server-side hd, /admin
  │  HM-006: User Authentication — Email + Google OAuth,
  │          регистрация, верификация, сброс пароля
  │          (после Cloud SQL: HM-GCP-003)
  ▼
Phase 2 — Knowledge Base
  │  загрузка и индексация нормативов и документов,
  │  справочники дефектов/материалов/оборудования,
  │  документный RAG: «спроси у нормативов»
  ▼
Phase 3 — AI Inspection
  │  мобильные осмотры с фото, Vision-анализ дефектов,
  │  мультимодальный поиск, генерация актов и отчётов
  ▼
Phase 4 — Predictive Maintenance
  │  накопленная история → прогноз деградации систем,
  │  планирование ремонтов до отказа, приоритизация бюджета
  ▼
Phase 5 — Digital Twin
     цифровой двойник здания: состояние всех систем
     в реальном времени, сценарное моделирование,
     масштабирование на жилой фонд города
```

| Фаза | Результат для пользователя | Ключевой архитектурный шаг |
|---|---|---|
| 1. Authentication | Сотрудники входят через Workspace (HM-005); клиенты — по любому e-mail или Google (HM-006) | Два контура аутентификации (ADR-0004) + RBAC + IAM |
| 2. Knowledge Base | Инженер задаёт вопрос — получает ответ со ссылкой на пункт СНиП | Документный конвейер: OCR → чанки → Vector Search → Gemini |
| 3. AI Inspection | Мастер фотографирует дефект — система его распознаёт и предлагает решение | Мультимодальный RAG, офлайн-PWA для полевой работы |
| 4. Predictive Maintenance | Система предупреждает о вероятных отказах заранее | Аналитический контур на BigQuery, прогнозные модели |
| 5. Digital Twin | Полная цифровая модель дома и фонда | Интеграция телеметрии, сценарное моделирование |

Каждая фаза даёт самостоятельную ценность и опирается на предыдущую — система развивается без переписывания фундамента.
