Чек-лист обязателен перед принятием каждого нового ADR и перед merge любого PR, затрагивающего архитектурные границы системы.

---

## Checklist

### Разделение контекстов

- [ ] Решение не переносит Personal Data в Service Context (GCP)
- [ ] Решение не переносит Service Data в Personal Context без обоснования
- [ ] Новые сущности классифицированы по критерию «субъект данных» (физлицо → Personal Context, организация/объект → Service Context)

### AI-конвейер

- [ ] AI-сервисы получают только Service Data или обезличенные агрегаты
- [ ] Personal Data не передаётся в Vertex AI, Vector Search или Gemini ни напрямую, ни косвенно

### Personal Context

- [ ] Решение не создаёт зависимость прикладной логики от конкретного KZ-провайдера
- [ ] Смена провайдера Personal Context остаётся конфигурационным изменением, не требующим правки кода
- [ ] Используются только возможности PostgreSQL, не препятствующие миграции между провайдерами

### Cross-context Communication

- [ ] Взаимодействие между контекстами осуществляется только через Reference Identity (UUID) и агрегированные данные
- [ ] Прямые соединения между хранилищами разных контекстов отсутствуют
- [ ] Отказ одного контекста не приводит к повреждению данных другого

### Architectural Invariants

- [ ] Решение не нарушает ни один из Invariants 1–6 (ADR-0005)
- [ ] Если нарушение инварианта неизбежно — выпускается новый ADR с явным обоснованием

### Совместимость с принятыми решениями

- [ ] Решение совместимо с ADR-0002 (GCP First)
- [ ] Решение совместимо с ADR-0003 (Cloud SQL)
- [ ] Решение совместимо с ADR-0004 (Two Auth Contours)
- [ ] Решение совместимо с ADR-0005 (Dual-Context Architecture)

### Уровень абстракции

- [ ] ADR содержит только архитектурное решение (что и почему), не реализацию (как именно)
- [ ] Детали реализации (Terraform, Prisma, Cloud Run config) вынесены в инженерные задачи
- [ ] Новый разработчик может понять решение без чтения исходного кода

---

## Использование

При открытии нового ADR: скопировать чек-лист в PR-описание и пройти каждый пункт.

При merge PR с архитектурными изменениями: reviewer проверяет чек-лист до approve.

Незакрытый пункт — не блокер merge по умолчанию, но требует явного комментария «принято осознанно, потому что...».
